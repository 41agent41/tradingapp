# Agent Install Runbook

**What this is:** a specification an AI agent (or a person) can execute top to
bottom to install TradingApp in **paper mode**, unattended except where an
operator's credential or a GUI login is genuinely needed. It drives three
idempotent scripts in [`install/`](install/) and ends with a machine-checked
report.

**What it is not:** a replacement for the guides it automates. Why each step
exists is explained in [`PROXMOX_DEPLOYMENT.md`](PROXMOX_DEPLOYMENT.md),
[`DEPLOYMENT.md`](DEPLOYMENT.md), [`mt5_sidecar/README.md`](mt5_sidecar/README.md)
and [`.env.example`](.env.example). When a step fails, the section linked from
it is where the fix is.

| Script | Runs on | Does |
|---|---|---|
| [`install/proxmox-create-ct.sh`](install/proxmox-create-ct.sh) | Proxmox VE host | Creates the app LXC with the Docker-in-LXC features (§4.1 / Appendix A) |
| [`install/install.sh`](install/install.sh) | App host (LXC, VM, bare metal) | Docker, deploy user, repo, `.env`, schema, stack, verification, boot unit |
| [`install/mt5-sidecar-wine.sh`](install/mt5-sidecar-wine.sh) | MT5 host (Linux VM or privileged LXC) | Wine, Windows Python, MT5 terminal, sidecar service, check |

---

## 0. Rules for the agent

These are not suggestions. Each one exists because breaking it can lose money
or lock the operator out.

1. **Paper only.** Never set `LIVE_TRADING_ENABLED=true` (in `.env` or on
   the Settings page),
   `SYSTEMATIC_EXECUTION_ENABLED=true`, `ALPACA_PAPER=false`,
   `OANDA_ENVIRONMENT=live`, `MT5_ALLOW_REAL=true`, an IB live port
   (4001/7496), or `account_mode: "live"` in `BROKER_CONNECTIONS`. The scripts
   refuse all of these with exit code 3; do not work around a refusal. Going
   live is the operator's decision, made by hand
   ([`DEPLOYMENT.md` § Enabling live trading](DEPLOYMENT.md#enabling-live-trading)).
2. **Never invent an operator input.** Broker logins and passwords, API keys,
   Telegram tokens, heartbeat URLs, IP plans and an external database's
   password come from the operator (§1). If one is missing, ask for it, or
   skip the optional component that needs it and say so. Random internal
   secrets (`API_TOKEN`, `SESSION_SECRET`, `BROKER_SERVICE_TOKEN`,
   `REDIS_PASSWORD`, the bundled database password, MT5 bridge secrets) are
   generated by the scripts; do not choose them yourself.
3. **Never print a secret** into chat, a ticket, a commit or a log you keep.
   Say where it is (`/opt/tradingapp/.env`, key `APP_PASSWORD`) instead.
4. **Stop on a FAIL.** Every step has a pass condition. On a failure, run the
   step's diagnosis, fix only what the linked section describes, re-run the
   step, and if it still fails, stop and report (§9). Do not skip ahead:
   later steps assume earlier ones held.
5. **Re-running is safe; editing by hand is not.** Every script checks before
   it changes anything. To change a setting, edit the answers file and re-run
   `install.sh env deploy verify`; do not edit `.env` directly unless the
   operator asks you to.
6. **Do not open ports to the internet** or change the Proxmox firewall
   unless the operator asks; §10 of the Proxmox guide is theirs to apply.
7. **Exit codes mean something.** `0` done; `1` a step failed (read the
   output); `2` an input is missing or invalid (ask the operator); `3`
   refused for safety (stop and report); `4` (MT5 script) the operator must
   act in the terminal's screen.

## 1. Inputs

Collect these before starting. "Agent" means the agent can decide or detect
it; everything else must come from the operator.

| Input | Needed for | From | Notes |
|---|---|---|---|
| Target: Proxmox host, or an existing Ubuntu 22.04+/Debian 12+ host | everything | operator | Root SSH (or `pct exec`) to it |
| App host IP (CIDR), gateway, bridge, CT id, storage | Proxmox only | operator | Must not be in `172.20.0.0/16` (the stack's Docker network) |
| Database: bundled or external | `INSTALL_DB_MODE` | operator, default **bundled** | External needs host, password and §5.3 of the Proxmox guide done first |
| Browser login password | `APP_PASSWORD` | operator, or generated | Generated if not given; the operator reads it from `.env` |
| IB Gateway host, paper account | IB, optional | operator | Gateway install needs a one-time GUI login (Proxmox guide §6) |
| MT5 **demo** account(s): login, password, server, broker server time zone | MT5, optional | operator | One terminal and sidecar per account; same account currency for all |
| MT5 host: a Linux VM/privileged LXC, or a Windows VM | MT5, optional | operator | Not the app container (it is unprivileged) |
| Alpaca paper key/secret, OANDA practice token/account | cloud brokers, optional | operator | |
| Telegram bot token and chat id | alerts, recommended | operator | Created with @BotFather |
| Heartbeat URL (and `/fail` URL) on a monitor **off this host** | dead-man's switch, recommended | operator | e.g. a healthchecks.io check, period 1 min, grace 5 min |

With none of the optional inputs, the result is a working app with no broker
connected: charts and orders need a venue, everything else runs.

## 2. Phase P — Proxmox container (skip on an existing host)

**P1. Check the hypervisor.** On the Proxmox host:

```bash
pveversion
pvesm status
chronyc tracking | grep -E 'Leap status|System time'
```

**Pass:** Proxmox VE 8 or later; the chosen storage is listed; leap status
`Normal`. Containers take their clock from the host, so a host without
working NTP is a FAIL ([§3.3](PROXMOX_DEPLOYMENT.md#33-time-synchronisation-not-optional-and-host-only)).

**P2. Create the app container.** Fetch the scripts onto the host and run:

```bash
mkdir -p /root/tradingapp-install && cd /root/tradingapp-install
for f in proxmox-create-ct.sh install.sh install.answers.example mt5-sidecar-wine.sh; do
  curl -fsSLO "https://raw.githubusercontent.com/41agent41/tradingapp/master/install/$f"
done
chmod +x *.sh

# Single container with the bundled database (Appendix A sizing):
./proxmox-create-ct.sh --ctid 110 --ip 10.7.3.20/24 --gw 10.7.3.1 \
  --storage local-lvm --bundled-db
# With an external database (§4.1 sizing): drop --bundled-db.
```

**Pass:** exit 0 and `container 110 is up ... and resolves names`. The script
adds `fuse=1` itself on ZFS storage.
**If it fails:** exit 1 on an existing CT names the missing feature and the
`pct set` that fixes it; anything else, see
[§15](PROXMOX_DEPLOYMENT.md#15-proxmox-specific-troubleshooting).

**P3. Hand the installer to the container.**

```bash
pct exec 110 -- mkdir -p -m 700 /etc/tradingapp
pct push 110 install.sh /root/install.sh --perms 0755
pct push 110 install.answers.example /etc/tradingapp/install.answers --perms 0600
```

From here every command runs **inside** the app host, as root
(`pct enter 110`, or `pct exec 110 -- <command>`).

---

## 3. Phase A — Answers file

**A1. Fill in `/etc/tradingapp/install.answers`.** On an existing host, fetch
`install.sh` and the example the same way as P2, then
`install -d -m 700 /etc/tradingapp && install -m 600 install.answers.example /etc/tradingapp/install.answers`.

The example documents every key. For a first install, the minimum is nothing
at all: bundled database, detected IP, generated secrets. Add:

- `INSTALL_DB_MODE=external` plus `POSTGRES_HOST`, `POSTGRES_PASSWORD`,
  `POSTGRES_SSL` for an external database;
- `IB_HOST` (and `IB_PORT=4002`) if an IB Gateway is ready;
- `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `HEARTBEAT_URL`,
  `HEARTBEAT_FAIL_URL` if the operator gave them;
- brokers are added in Phase B, after the base install passes.

**Pass:** `stat -c %a /etc/tradingapp/install.answers` prints `600`, and the
file contains only values the operator gave you or the defaults.

## 4. Phase I — Install

**I1. Run every phase.**

```bash
/root/install.sh all
```

This takes several minutes on the first run (images build). It prints
`[install]` lines per phase and ends with the verification table. The full
log is `/var/log/tradingapp-install/install.log`.

**Pass:** exit 0, and the last lines read `result: PASS` and
`done: preflight docker user repo env schema deploy verify service`.

**If it fails,** the phase that failed is the last `[install]` line before
`ERROR`. Re-run from that phase once the cause is fixed (for example
`/root/install.sh deploy verify service`).

| Phase | Typical failure | Where the fix is |
|---|---|---|
| preflight | address in 172.20.0.0/16; disk; cannot reach GitHub | Proxmox guide §2; network |
| docker | daemon will not start; `hello-world` fails; `vfs` driver | §4.2, §15 Docker-in-LXC (`nesting`, `keyctl`, `fuse` on ZFS) |
| repo | local changes / diverged checkout | someone edited `/opt/tradingapp`; ask the operator before discarding |
| env | exit 2 naming a key; exit 3 | ask the operator for the key; for 3, see §0 rule 1 |
| schema | cannot connect (external) | Proxmox guide §5.3–5.4 (`pg_hba.conf`, password, extension) |
| deploy | `refusing to start: <reason>` | the reason names the key; [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md) |
| verify | any `CHECK ... FAIL` | table in I2 |

**I2. Read the report.** `cat /var/log/tradingapp-install/report.txt`. Each
check is one line, `CHECK <id> PASS|FAIL|SKIP <detail>`:

| Check | Proves | On FAIL |
|---|---|---|
| V1 | every container is running | `docker compose ps`; `./tradingapp.sh logs` |
| V2 | backend healthy: database and broker service reachable | detail names the failing side |
| V3 | database reachable from the backend | external: §5.4 of the Proxmox guide |
| V4 | broker service answers on loopback | `./tradingapp.sh logs` |
| V5 | frontend serves | rebuild: `install.sh deploy` |
| V6 | the API refuses an unauthenticated call and accepts `API_TOKEN` | `.env` `API_TOKEN` vs. the running container: `install.sh deploy` |
| V7 | the broker service refuses calls without its token | as V6, for `BROKER_SERVICE_TOKEN` |
| V8 | the broker service is not published on the LAN | someone changed `docker-compose.yml` |
| V9 | `order_executions` keyed per connection (paper runbook step 3) | re-run `install.sh schema` |
| V10 | no startup refusals in the backend log | the log line names the key |
| V11 | paper mode | §0 rule 1: stop and report |
| V12 | `.env` mode 600, owned by the deploy user | `install.sh env` |
| V13 | each `BROKER_CONNECTIONS` entry registered as paper | the detail carries the manifest error |
| V14 | each MT5 sidecar: reachable, demo account, refuses no-secret calls | Phase B2 |
| V15 | IB Gateway socket reachable | Proxmox guide §6.5 (trusted IPs, firewall) |
| V16 | dead-man's switch pinging | wait a minute and re-run `install.sh verify` |

SKIP is not a failure: it means the optional component is not configured.

**I3. Confirm in a browser (operator).** Tell the operator to open
`http://<SERVER_IP>:3000` and log in with `APP_PASSWORD` from
`/opt/tradingapp/.env` (`sudo grep ^APP_PASSWORD= /opt/tradingapp/.env`).
**Pass:** the operator confirms the dashboard loads after login.

**I4. Snapshot (Proxmox).** On the host:
`pct snapshot 110 clean-install --description "install.sh all: PASS"`.
**Pass:** `pct listsnapshot 110` shows it. Directory storage cannot snapshot;
note that in the report rather than failing.

## 5. Phase B — Brokers (each optional)

Add one broker at a time and re-verify after each, so a failure has one cause.

### B1. IB Gateway

The Gateway is a logged-in GUI session with a one-time configuration over VNC
([Proxmox guide §6](PROXMOX_DEPLOYMENT.md#6-create-the-ib-gateway-container)).
The agent can create the container and install the packages (§6.1–6.2); the
**operator** logs in to the **paper** account and sets the API options
(§6.3), because that needs their IB credentials and a screen. Then:

1. Answers: `IB_HOST=<gateway ip>`, `IB_PORT=4002`.
2. `/root/install.sh env deploy verify`

**Pass:** V15 PASS. Then, as the deploy user,
`curl -s -H "X-Broker-Service-Token: $(sudo grep ^BROKER_SERVICE_TOKEN= /opt/tradingapp/.env | cut -d= -f2)" http://127.0.0.1:8000/connection`
reports `connected: true` once a market-data route has been used.

### B2. MT5 demo account(s)

One terminal, one sidecar, one port per account. Use a separate Linux VM or
privileged LXC (Wine), or a Windows VM; never the app container.

1. **Declare the connection** in the answers, one JSON line, `paper` only:

   ```
   BROKER_CONNECTIONS='[{"id":"broker-a-demo","platform":"mt5","url":"http://10.7.3.23:9100","secret_env":"MT5_SECRET_A","account_mode":"paper","currency":"USD","default":true}]'
   PORTFOLIO_BASE_CURRENCY=USD
   DEFAULT_BROKER=mt5
   ```

   Remove `MT5_BRIDGE_URL`/`MT5_BRIDGE_SECRET` if present: the app refuses
   both styles at once.

2. **Generate its secret:** `/root/install.sh env`. It creates `MT5_SECRET_A`
   in `.env`. **Pass:** `grep -c ^MT5_SECRET_A= /opt/tradingapp/.env` prints 1.

3. **Install the sidecar on the MT5 host (Linux, Wine).** Copy
   `mt5-sidecar-wine.sh` there and pass the secret through the environment,
   not the command line. Ask the operator for the demo login, password,
   server and the broker server's time zone:

   ```bash
   export MT5_BRIDGE_SECRET='<MT5_SECRET_A from the app host .env>'
   export MT5_LOGIN=... MT5_PASSWORD=... MT5_SERVER=...     # from the operator
   ./mt5-sidecar-wine.sh install --instance broker-a --port 9100 --server-tz Europe/Athens
   unset MT5_BRIDGE_SECRET MT5_PASSWORD
   ```

   Use `--installer-url` for the broker's own MT5 installer if the operator
   names one. **Pass:** exit 0 and `check: PASS (demo account ...)`.
   **Exit 4** means the operator must act in the terminal: run
   `./mt5-sidecar-wine.sh vnc --instance broker-a`, tell the operator to
   tunnel (`ssh -L 5900:localhost:5900 root@<mt5 host>`) and connect a VNC
   viewer to `localhost:5900`, log in if needed, and switch **Algo Trading**
   on. Then `./mt5-sidecar-wine.sh check --instance broker-a`.

   **Windows instead:** follow [`mt5_sidecar/README.md` § Windows](mt5_sidecar/README.md#windows)
   with `MT5_BRIDGE_SECRET` set to the same value, `MT5_ALLOW_REAL=false`,
   and the firewall rule for the port scoped to the app host's IP only.

4. **Firewall the sidecar** to the app host only (Windows Firewall, `ufw`, or
   the Proxmox firewall). Anything that reaches the port with the secret can
   trade the account.

5. **Re-deploy and verify** on the app host: `/root/install.sh deploy verify`.
   **Pass:** V13 lists `mt5:broker-a-demo` as paper; V14 PASS. The quote
   clock check in [`mt5_sidecar/README.md` § Checking it](mt5_sidecar/README.md#checking-it)
   confirms `--server-tz`: a quote's time within seconds of `date -u +%s`
   while the market is open.

A second account repeats 1–5 with its own `id`, `secret_env`, instance name
and port.

### B3. Alpaca paper / OANDA practice

Credentials only, no host. In the answers, add the connection with
`account_mode: "paper"` and its key names, plus the values from the operator:

```
BROKER_CONNECTIONS='[{"id":"alpaca-paper","platform":"alpaca","key_env":"ALPACA_KEY_A","secret_key_env":"ALPACA_SECRET_A","account_mode":"paper","currency":"USD","default":true}]'
ALPACA_KEY_A=...
ALPACA_SECRET_A=...
```

(One `BROKER_CONNECTIONS` line holds every connection; merge entries into the
one list.) Then `/root/install.sh env deploy verify`. **Pass:** V13 lists it.
Exit 2 naming a key means its value is missing from the answers.

## 6. Phase S — Safety nets

Recommended before anything runs unattended; required before the paper
runbook's execution steps.

1. Answers: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `HEARTBEAT_URL`,
   `HEARTBEAT_FAIL_URL` (operator-supplied). Keep `KILL_SWITCH_ACTION=notify`.
2. `/root/install.sh env deploy`, wait two minutes, `/root/install.sh verify`.

**Pass:** V16 PASS and the operator sees the heartbeat check turn green on
their monitor. The deliberate failure tests (stopping the backend and being
paged) are in [`PAPER_DEPLOYMENT_RUNBOOK.md` step 22](PAPER_DEPLOYMENT_RUNBOOK.md#22-confirm-the-alerting-path);
they page the operator, so agree a time with them first.

---

## 7. Phase R — Reboot test

The boot unit only matters if it works after a reboot, and in an LXC every
host kernel update is one.

1. Outside market hours, with the operator's agreement:
   `reboot` (VM/bare metal) or `pct reboot 110` (Proxmox host).
2. When the host is back: `/root/install.sh verify`.

**Pass:** `result: PASS` with no other action taken. On a Proxmox host with
separate guests, set boot order first ([§13](PROXMOX_DEPLOYMENT.md#13-boot-order-and-auto-start)).

## 8. Upgrades and changes

Same script, same answers:

```bash
/root/install.sh repo env schema deploy verify
```

`repo` fast-forwards to `INSTALL_REF` and refuses if someone changed tracked
files; `schema` re-applies the canonical schema (idempotent) before the new
code starts; `deploy` rebuilds. Snapshot first on Proxmox
(`pct snapshot 110 pre-upgrade-$(date +%F)`); rolling back is
`pct rollback 110 <name>`.

`env` never rotates a secret that is already set and never changes a value
you did not put in the answers, with one exception: `CORS_ORIGINS` and
`IB_CORS_ORIGINS` follow `SERVER_IP` while they still hold
the value derived from it. Once they hold anything else (an https origin
behind nginx), they are left alone.

## 9. Report to the operator

When done, or when stopped, send:

1. The outcome: `PASS`, or the phase and step that stopped, with the exit
   code.
2. The contents of `/var/log/tradingapp-install/report.txt` (it holds no
   secrets).
3. The URL, and that the login password is `APP_PASSWORD` in
   `/opt/tradingapp/.env` on the app host.
4. What was skipped and the input it needs (for example "MT5: no demo login
   given").
5. Anything only the operator can do next: a VNC login, the TLS front door
   ([§10](PROXMOX_DEPLOYMENT.md#10-reverse-proxy-tls-and-firewalling)),
   firewall rules, backups ([§12](PROXMOX_DEPLOYMENT.md#12-backups-and-snapshots)).

## 10. After the install

The install ends at a verified, paper-mode, signal-free system. What comes
next is the operator's evaluation, not part of installing:

- [`PAPER_DEPLOYMENT_RUNBOOK.md`](PAPER_DEPLOYMENT_RUNBOOK.md) takes two MT5
  demo accounts through the fleet view, signal-only running, paper execution
  and a week of notify-only observation. Its steps 3–4 and 5–10 are already
  covered by V9/V10 and Phase B2; start it at step 11.
- Turning on `SYSTEMATIC_ENABLED`, `EXECUTIONS_SYNC_ENABLED` and later
  `SYSTEMATIC_EXECUTION_ENABLED` happens there, on paper, one at a time.
- Live trading is out of scope for any agent following this runbook
  ([§0 rule 1](#0-rules-for-the-agent)).
